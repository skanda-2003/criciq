# CricIQ: IPL Tactical Analytics Dashboard

## Project Overview

CricIQ is a full-stack cricket analytics project built around ball-by-ball IPL data. The goal is to answer questions that IPL coaching staff and analysts actually care about — not just batting averages, but phase-based performance, bowler matchups, venue effects, win probability, and a composite player impact metric.

## Tech Stack

- **Language**: Python 3.11
- **Data**: Pandas, NumPy
- **ML**: Scikit-learn, Scipy
- **Visualization**: Matplotlib, Seaborn, Plotly
- **Dashboard**: Streamlit
- **Environment**: Jupyter Notebooks for analysis → `.py` files for the Streamlit app

## Data Sources

- **Primary**: Cricsheet IPL data (cricsheet.org) — ball-by-ball JSON/CSV for every IPL match since 2008. 1000+ matches, every delivery recorded.
- **Secondary**: Kaggle IPL Player Performance Dataset — career aggregates and auction prices for player valuation angle.

## Core DataFrames

Two primary DataFrames drive all analysis. Both live in `data/processed/` and are generated by running `main.py`. The decision to pre-flatten all Cricsheet JSON data into two canonical DataFrames was intentional — it separates data engineering from analysis cleanly, avoids re-parsing nested JSON on every query, and means all downstream notebooks and the Streamlit app work from the same consistent source of truth.

**1. Ball-by-ball DataFrame (`deliveries.csv`)** — 279,586 rows, one per delivery:

| Column | Description |
|--------|-------------|
| `match_id`, `season`, `venue`, `city` | Match identifiers |
| `innings`, `batting_team`, `bowling_team` | Innings context |
| `over` (1-indexed), `ball_in_over` (legal balls only) | Ball position |
| `batter`, `non_striker`, `bowler` | Players on field |
| `batter_runs`, `extra_runs`, `total_runs` | Runs breakdown |
| `is_wide`, `is_noball`, `is_boundary_4`, `is_boundary_6`, `is_dot`, `wicket` | Boolean flags |
| `wicket_kind`, `player_out`, `fielders` | Wicket details |
| `phase` | `"powerplay"` / `"middle"` / `"death"` — pre-computed per ball |
| `cumulative_runs`, `cumulative_wickets` | Running totals per innings (needed for win probability) |
| `match_winner` | Result carried into every row |
| `batting_position` | Batting order position (1 = opener) — needed for Angle 1 |
| `target_runs`, `target_overs` | 2nd innings only — needed for required run rate in Angle 4 |
| `super_over` | Boolean — exclude super over balls from all stats |
| `current_run_rate` | Cumulative runs / overs completed — computed per ball, needed for Angle 4 |
| `required_run_rate` | Runs remaining / overs remaining — 2nd innings only, needed for Angle 4 |
| `run_rate_pressure` | `required_run_rate / current_run_rate` — domain-motivated pressure ratio, needed for Angle 4 |

> **Note on `is_dot`:** A ball is flagged dot only if `batter_runs == 0` AND the extras dict is empty. Leg byes (0 batter runs but non-empty extras) are NOT counted as dots — this is intentional; document if you change it.

> **Note on `run_rate_pressure`:** This feature was engineered based on how analysts actually think about chase situations — the ratio of required run rate to current run rate captures pressure better than either number alone. A value > 1.5 typically indicates a team is significantly behind the chase. Set to `NaN` for 1st innings rows and for balls before over 1 is complete (avoid divide-by-zero).

**2. Match-level summary DataFrame (`matches.csv`)** — 1,175 rows, one per match:

| Column | Description |
|--------|-------------|
| `match_id`, `season`, `date`, `venue`, `city` | Identifiers |
| `team1`, `team2`, `toss_winner`, `toss_decision` | Teams and toss |
| `winner`, `result`, `result_margin_runs`, `result_margin_wickets` | Outcome |
| `player_of_match` | Award |

## The 5 Analysis Angles

### Angle 1 — Phase-wise Batting Analysis
- Phases: Powerplay (overs 1–6), Middle (7–15), Death (16–20)
- Metrics per batsman per phase: strike rate, boundary %, dot ball %
- Question: Who accelerates in the death? Who struggles in the powerplay?
- Minimum threshold: 100 balls faced per phase before including a batsman in phase rankings — avoid small sample size distortion

### Angle 2 — Bowler Matchup Analysis
- Filter: bowler-batsman combinations with >20 balls faced
- Metrics: runs per ball, dismissal probability, boundary rate
- Output: matchup heatmap matrix
- **Extension**: Cluster batsmen by vulnerability profile across bowler types (pace vs spin, left-arm vs right-arm) using k-means clustering — target 3–4 archetypes (e.g. spin-vulnerable, pace-vulnerable, all-surface). This adds unsupervised ML to the project naturally and turns the heatmap from a visualization into a finding.

### Angle 3 — Venue and Pitch Impact
- Compare scoring at different venues (e.g. Wankhede vs Chepauk)
- Use t-tests (Scipy) to test statistical significance of venue differences
- Report p-values — this makes it research-grade, not just descriptive
- **Also report effect size (Cohen's d) alongside every p-value** — statistical significance alone doesn't tell you if the venue difference is practically meaningful. A p-value of 0.001 with Cohen's d of 0.08 is technically significant but practically irrelevant. Document this distinction in the notebook and README.

### Angle 4 — Win Probability Model (ML centrepiece)
- Features: `current_run_rate`, `required_run_rate`, `run_rate_pressure` (engineered), `wickets_in_hand`, `overs_remaining`, `venue` (encoded), `batting_team` (encoded)
- The `run_rate_pressure` feature was domain-motivated — analysts think in terms of rate ratios, not raw rates independently. Always explain this decision when presenting the project.
- Models: Logistic Regression (baseline) → Random Forest
- Evaluation: accuracy, ROC-AUC, calibration curve
- Output: ball-by-ball win probability shifts for a sample match
- Calibration curve is non-negotiable — it validates that predicted probabilities are reliable, not just that the classifier is accurate

### Angle 5 — Player Impact Score (original metric)
- Composite score weighing batting contribution, bowling economy, and fielding (catches, run outs)
- Produces a per-match impact score and season leaderboard
- Goal: identify players who outperform their reputation by this metric

**Provisional weighting table** (document rationale for any changes):

| Component | Weight | Rationale |
|-----------|--------|-----------|
| Batting (runs scored vs phase average) | 50% | Primary match impact driver |
| Bowling (economy vs venue average) | 35% | Adjusted for conditions, not raw economy |
| Fielding (catches + run outs) | 15% | Hardest to replace; limited by data availability |

> **Note on fielding**: Cricsheet data only records catches and run-outs from wicket records — it does not include fielding position or diving stops. This means the fielding component is an undercount. Acknowledge this explicitly in the README and dashboard.

## Hypotheses (Pre-Analysis)

Writing hypotheses before running analysis is a research discipline. These are expectations to test, not conclusions.

- Death-over specialists will show SR > 180 in overs 17–20 but SR < 120 in powerplay, suggesting role-specific batsmen are being correctly deployed
- Wankhede (Mumbai) will show significantly higher scoring rates than Chepauk (Chennai) due to pitch and boundary differences — expect Cohen's d > 0.3
- The `run_rate_pressure` feature will rank among the top 3 feature importances in the Random Forest model
- At least 2–3 players per season will rank in the top 10 by Player Impact Score but outside the top 20 by conventional stats — these are the "undervalued" findings worth highlighting

## Known Limitations

Document these honestly in the README — acknowledging limitations is a sign of analytical maturity, not weakness.

- **Fielding data is incomplete**: Cricsheet only records catches and run-outs from wicket metadata. Fielding stops, misfields, and direct throws are not captured. The fielding component of the Player Impact Score is therefore an undercount.
- **Player name inconsistencies**: Cricsheet uses different name spellings across seasons. `src/name_map.py` handles known cases but may miss edge cases — validate by checking if any player appears twice with slightly different names in career aggregates.
- **Venue conditions change over time**: The same venue (e.g. Eden Gardens) plays differently across seasons due to pitch preparation changes. The venue t-test treats all seasons as one population — this is a simplification worth noting.
- **Win probability model is 2nd innings only**: The current feature set (required run rate, run rate pressure) only applies to chases. 1st innings win probability would require a different model architecture — this is a known scope limitation.
- **No player auction price validation**: The Kaggle auction price data is used for the "outperforming reputation" angle but auction prices reflect expected future performance, not just past stats. The comparison is indicative, not rigorous.

## Key Implementation Notes

- Cricsheet JSON is nested — flattening takes care; budget time for this in Week 1
- Player names vary across seasons — `src/name_map.py` handles this; must be called from `main.py` before saving CSVs
- `src/__init__.py` must exist (empty file) for imports to work in notebooks and the Streamlit app
- Calibration curve is essential for win probability model — it validates that predicted probabilities are reliable
- The venue t-test p-values and Cohen's d should be reported explicitly in the dashboard and README
- Win probability model needs `target_runs`, `target_overs`, `current_run_rate`, `required_run_rate`, and `run_rate_pressure` columns — verify all five exist in `deliveries.csv` before starting Week 3
- `super_over` flag must be set in parser and filtered out before computing any career stats
- Apply minimum ball thresholds before all per-player rankings to avoid small sample distortion (suggested: 100 balls for batting angles, 50 balls bowled for bowling angles)
